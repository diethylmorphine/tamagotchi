# Атомарное хранение действий и игровых наград

## Контекст

`PetRepository.save()` защищает одну строку pet через version. Новые задания и кошелёк требуют согласованного обновления нескольких таблиц. Сетевой таймаут не означает, что действие не произошло.

## Решение

Предлагается сохранить расчёт правил в Python и ввести Postgres RPC для атомарной фиксации pet, события, дневного прогресса и ответа по ключу идемпотентности. Получение награды и будущая покупка используют отдельные транзакционные RPC. Блокировки строк и уникальные бизнес-ключи защищают от разных UUID для одной награды. У повторного ключа проверяется payload. Только проверенный backend вызывает RPC.

## Последствия

Границы атомарности становятся явными; появляется SQL-код, которому нужны интеграционные тесты. Изменения выполняются аддитивно и включаются после миграции. Реестр ключей не очищается без отдельного решения о повторных запросах. Клиентский busy-флаг остаётся UX-механизмом, не защитой баланса.

## Альтернативы

Последовательные REST-запросы не обеспечивают откат. Глобальная Python-блокировка не защищает несколько экземпляров приложения. Полный перенос `act/evolve` в SQL дублирует хорошо отделённую игровую логику. Выбрана граница: Python рассчитывает, Postgres атомарно проверяет версию и сохраняет.
