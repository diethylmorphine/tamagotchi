# Живой питомец и ежедневный прогресс

Питомец показывает свои потребности, открывает титулы с ростом и получает листочки за разнообразный ежедневный уход.

<details>
<summary><b>Проблема и контекст</b></summary>
<br>

Четыре кнопки восстанавливают показатели, но уровень пока не даёт новой цели. Повторяющиеся действия нуждаются в эмоциональной обратной связи. Основание: [анализ проекта](../research/2026-09-12-0206-feature-opportunities-review.md). Текущая игровая логика и Telegram-авторизация переиспользуются. Сон уже есть, рейтинг разрабатывается параллельно.

</details>

<details>
<summary><b>Цель, архитектура и ограничения</b></summary>
<br>

Goal: Добавить реакции, вехи и ежедневные задания без потери текущего прогресса.

Architecture: Чистые правила Python, серверная авторизация, атомарные транзакции Postgres, HTML/CSS/JS без сборки.

Tech Stack: FastAPI, aiogram 3, Supabase Postgres, Vercel, vanilla JavaScript.

Global Constraints: Сервер определяет время и награды; один питомец на Telegram ID; питомец не умирает; сон сохраняет текущие правила; миграции аддитивные; существующие незакоммиченные изменения сохраняются.

Игрок MUST видеть следующую достижимую цель. Пропущенный день MUST NOT обнулять заработанное. Повтор HTTP-запроса MUST NOT повторять действие или награду.

</details>

<details>
<summary><b>Поведение и интерфейсы</b></summary>
<br>

**Реакции.** `present()` получает поля `mood: str` и `next_milestone: object | null`. Приоритет состояния: sleeping при активном сне; иначе потребность с минимальным показателем ниже 30; иначе happy при всех показателях >=70; иначе calm. Ничьи потребностей решаются порядком satiety, energy, hygiene, happiness. Значения mood: sleeping, hungry, tired, dirty, lonely, happy, calm. Состояние вычисляется по `evolve()` на сервере. Подпись объясняет потребность; анимация имеет текстовый эквивалент и учитывает prefers-reduced-motion.

**Вехи.** Уровни 2, 5, 10 открывают титулы «Знакомые», «Друзья», «Неразлучные». Это отображение текущего уровня, без выдачи валюты или XP. Поле `current_title: str` содержит последний доступный титул; до уровня 2 используется «Первая встреча». Старые игроки сразу видят доступный титул. При административном снижении уровня титул пересчитывается. `next_milestone` содержит `level: int`, `title: str`, `xp_remaining: int`; после уровня 10 возвращается null.

**Задания.** Новый `GET /api/progression` возвращает `day` (YYYY-MM-DD UTC), `resets_at` (ISO UTC), `balance: int`, `tasks: [{id, progress, target, reward, claimed}]`. Три фиксированные задачи: care_once (одно успешное действие, target=1, reward=5), care_variety (два разных вида ухода, target=2, reward=10), care_three (три успешных действия, target=3, reward=10). Старт сна считается rest один раз; тики сна, отказы, чтения, админские изменения и переименование не считаются. Эти задания совместно выполнимы без play. Нет отдельной награды за вход и streak.

Один день определяется серверной UTC-датой в момент фиксации действия; интерфейс явно показывает время сброса. Новые сутки создаются логически при обращении, cron не нужен. У старых игроков отсчёт начинается после выпуска, прошлые события не выдумываются. Неполученные награды можно забрать за прошедшие дни: API принимает явную дату и хранит прогресс. Начальный UI показывает сегодня и список дней с неполученными наградами.

`POST /api/progression/claims`: `{day: str, task_id: str}` плюс `Idempotency-Key: UUID`, ответ `{balance: int, claim: {day, task_id, reward}}`. Награды независимы; лимит 25 листочков за день. Валюта пока только копится, не влияет на рейтинг XP.

**Хранение.** Предлагаются `game_events` (event_id UUID, telegram_id, action, occurred_at, day), `daily_progress` (telegram_id, day, action_count, action_mask), `wallets` (telegram_id, balance), `reward_claims` (telegram_id, day, task_id, amount), `game_requests` (telegram_id, key UUID, operation, payload_hash, response JSONB). Все таблицы закрыты для anon/authenticated. Ограничения уникальности: событие по event_id, прогресс по владельцу и дню, claim по владельцу/дню/задаче, request по владельцу/key. Баланс >=0.

`PetRepository.commit_action(...)` вызывает новый Postgres RPC: проверяет request, блокирует pet, сравнивает version, атомарно пишет состояние, событие, дневной прогресс и сохранённый ответ. Расчёт состояния остаётся в Python; время транзакции задаёт день события. При конфликте версии Python перечитывает pet и заново вызывает `act`; частичные записи откатываются. Существующие rename/admin продолжают участвовать в version-контроле.

Повтор ключа с тем же payload возвращает исходный успешный ответ; другой payload с тем же ключом даёт 409. Replay проверяется до cooldown, иначе успешный повтор ошибочно отклонится. После replay UI перечитывает актуальные pet/progression. Claim выполняется одной транзакцией: проверка задания, уникальный claim, увеличение кошелька, сохранённый ответ. Запросы одного владельца сериализуют изменения кошелька. SQL-функции доступны только service_role; владелец всегда берётся из проверенного initData.

Клиент создаёт UUID один раз на намерение, сохраняет pending-запрос до подтверждения и повторяет с тем же ключом после сетевой ошибки. До разрешения pending новые действия не отправляются. Смена дня не меняет дату уже созданного claim. Сервер не принимает величину награды, XP или ID владельца от клиента.

</details>

<details>
<summary><b>Альтернативы, риски и открытые вопросы</b></summary>
<br>

Сначала магазин дал бы больше экранов, но без целей у валюты нет понятного источника. Сначала мини-игра потребовала бы проверки результата и новых ассетов. Реакции и вехи дают быстрый результат; задания создают основу следующего этапа.

Несколько последовательных REST-записей отвергнуты: сбой между выдачей награды и фиксацией claim создаёт дубли. Предложение транзакций зафиксировано в [ADR](../adr/0001-atomic-game-rewards.md).

Риски: увеличение сложности слоя хранения, рассинхронизация дней в UI, фарм повторных запросов, рост журнала. RPC MUST тестироваться на настоящем тестовом Postgres, а не только через fake repository. Политика очистки request/event пока не вводится: удаление dedupe-ключей может разрешить повторные выплаты. Перед широким запуском определить срок хранения и процедуру удаления аккаунта.

Баланс 25 листочков в день и пороги вех являются стартовым предложением, не подтверждённой пользовательскими данными оптимизацией. После первой тестовой недели оценить выполнимость заданий; до этого правила детерминированы как описано выше.

</details>

<details>
<summary><b>Проверка и разбиение работ</b></summary>
<br>

Проверить пороги 29.9/30/70, ничьи потребностей, сон и пробуждение, старые уровни и админское снижение. Для заданий проверить rest без тиков, отказы, разные действия, UTC-полночь, получение вчерашней награды. Два параллельных claim с разными ключами должны дать одну выплату. Потеря ответа после commit и повтор должны вернуть один результат. Другой пользователь не может прочитать чужой прогресс. Регрессии ухода, администрирования, рейтинга и сна обязательны.

Работы соответствуют задачам A1-A6 [плана](../plans/2026-09-12-0206-pet-growth-roadmap.md): реакции; вехи; транзакции; прогресс; UI; проверка выпуска.

Вне первого выпуска: прогулки, покупки, платежи, уведомления, мультипитомцы. Связанный следующий модуль описан [отдельно](2026-09-12-0206-exploration-room-collection.md).

</details>
